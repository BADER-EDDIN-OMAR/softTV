# تشغيل سوفت تيفي على سيرفر دائم

هذه الملفات جاهزة لتشغيل الموقع على سيرفر Linux مع Docker Engine وDocker Compose. لا تحتاج قاعدة بيانات مدفوعة منفصلة. تكلفة السيرفر والنطاق يحددها مزودك، ولا تضمن هذه الملفات استضافة مجانية.

## أول تشغيل

1. انقل المشروع إلى السيرفر، دون `data` أو `.git` أو كلمات مرور من بيئة التطوير. إن كان لديك بيانات حقيقية، انقلها كنسخة احتياطية آمنة عبر إجراء استعادة منفصل.
2. اربط نطاقًا أو نطاقًا فرعيًا بعنوان السيرفر عبر DNS. افتح المنافذ 80 و443. لا تفتح منفذ التطبيق 3000.
3. من مجلد المشروع أنشئ ملف `.env` خاصًا (لا تودعه في Git) يحتوي سطرًا واحدًا: `DOMAIN=requests.your-domain.com`، مع استبدال المثال بنطاقك الفعلي. بدون https أو مسار.
4. شغّل `docker compose up -d --build`. ينتظر الوكيل جاهزية التطبيق، ويصدر شهادة HTTPS تلقائيًا عند صحة DNS وإمكانية الوصول إلى النطاق.
5. اقرأ كلمة مرور الإدارة محليًا على السيرفر باستخدام `docker compose exec app cat /app/data/admin-password`، واحفظها في مدير كلمات المرور. لا ترسلها في المحادثة. لا يستخدم هذا النشر كلمة مرور التطوير.
6. افتح الموقع من نطاقك. لوحة الإدارة في `/admin`. أرسل طلبًا حقيقيًا تجريبيًا، افتح المرفق من الإدارة، ثم غيّر حالته وتابع الرد من صفحة العملاء.

`docker compose ps` لعرض الجاهزية، و`docker compose logs --tail=100 app web` للتشخيص. إعادة التشغيل: `docker compose restart`. التحديث بعد نقل الملفات: `docker compose up -d --build`. لا تستخدم `docker compose down -v` لأنه يحذف البيانات والشهادات.

التطبيق غير مكشوف مباشرة. `TRUST_PROXY=true` يسمح باستخدام عنوان العميل الذي يضعه Caddy لتحديد حدود الطلبات لكل عميل. لا تفعّل هذا الخيار عند كشف التطبيق مباشرة أو وضع وكيل لا يستبدل `X-Forwarded-For`.

## النسخ الاحتياطي

نفّذ `sh scripts/backup.sh` يوميًا من مجلد المشروع. يمكن تشغيله من cron لحساب مسموح له باستخدام Docker، مثل `0 3 * * * cd /path/to/softTV && sh scripts/backup.sh`. وقت cron حسب توقيت السيرفر. يتوقف التطبيق لوقت قصير أثناء النسخ، ثم يعود تلقائيًا. يكون مجلد `backups` خاصًا؛ انقل نسخة مشفرة إلى مكان آخر، ولا تعتمد على نسخة في نفس القرص فقط. النسخة تحتوي كلمة مرور الإدارة ومرفقات العملاء؛ تعامل معها كبيانات خاصة.

## الاستعادة

على نسخة الموقع المقصودة، مع الانتباه إلى أن الخطوات التالية تخص **وحدة بيانات فارغة فقط**:

1. أوقف التطبيق بـ `docker compose stop app`.
2. ضع ملف النسخة في مجلد `backups` وتحقق من مصدره. افحص قائمة المحتويات بـ `tar -tzf backups/BACKUP.tar.gz`.
3. استعد إلى الوحدة الفارغة باستخدام:

```sh
docker compose run --rm --no-deps -T --entrypoint sh app \
  -c 'test -z "$(ls -A /app/data)" || { echo "Target is not empty" >&2; exit 1; }; tar -xzf - -C /app/data' \
  < backups/BACKUP.tar.gz
docker compose up -d
```

استبدل `BACKUP.tar.gz` باسم الملف الصحيح. لا تمسح وحدة حالية لاستعادة نسخة فوقها دون أرشفة بياناتها أولًا. اختبر المتابعة والمرفقات بعد الاستعادة.

## حالة التحقق

اختبارات التطبيق المحلية موثقة في README الرئيسي. تحقّق من نتائج بناء Docker المذكورة في تسليم العمل؛ إصدار شهادة عامة وDNS والتشغيل على سيرفرك يحتاج الوصول إلى الاستضافة ولم يحدث تلقائيًا بإنشاء هذه الملفات.

تم التحقق داخل بيئة التطوير من بناء صورة Node، وتشغيل التطبيق بمستخدم غير جذر ونظام ملفات للقراءة فقط، وتقديم طلب وتسجيل دخول مع ملف جلسة Secure، والنسخ الاحتياطي والاستعادة إلى وحدة بيانات منفصلة. تم التحقق من صلاحية ملف Caddy؛ لم يُختبر إصدار شهادة عامة أو ربط DNS.
